  3．短問クイズとステップ式ドリルを分ける

  現行のposse-quiz-app/lib/quiz/sessionManager.ts:73は問題をランダムに選びます。この方式は用語確認や短問復習には適切ですが、前のコードを引き継ぐ演習には合いません。

  次の2つを併存させるのがよいです。

  - 短問モード：独立した問題を3・5・10問解く。既存の仕組みを活用する。
  - ドリルモード：1つの制作物を順序付きステップで完成させ、途中から再開する。

  基本構造は Week → Drill → Step とし、短問は1ステップのドリルとしても表現できます。

  特に、次の挙動は明文化してください。

  - 次のステップへ渡すのは、直前に合格した提出コードか、最新の下書きか。
  - 過去のステップを修正したとき、後続ステップの状態をどう扱うか。
  - 復習で途中のステップだけ出すとき、必要な開始コードをどう用意するか。
  - リセットは「そのステップ開始時」に戻すのか、「教材の初期コード」に戻すのか。

  おすすめは、合格したコードを次の開始状態として保存し、復習には独立した開始状態を用意する方式です。これなら前段の失敗で復習できなくなることを防げます。

  また、教材には「着手前に分解する」活動が繰り返しあります。穴埋めを細分化しすぎると、学習者が実装順序を考える機会を失います。最初の分解ステップと、支援を減らした仕上げ問題は残したいです。

  4．採点は本実装前に境界を変更する

  現在のposse-quiz-app/types/content.ts:46は、問題の配信データにcorrectOptionIdやcorrectTextを含みます。posse-quiz-app/lib/quiz/answerJudge.ts:28では、操作式は端末のactivityCompleted: trueを正解として扱っていま
  す。

  デモとしては自然ですが、本番では次の分離が必要です。

  - 公開する情報：問題文、選択肢、初期コード、編集範囲、公開の達成条件。
  - 非公開の情報：正解、非公開テスト、正式な採点ルール。
  - 提出する情報：選択内容、ファイル一式、操作履歴、問題の版。
  - サーバーが決める情報：正誤、条件別結果、得点、完了状態。

  端末が送ったisCorrectやactivityCompletedをそのまま保存してはいけません。

  ターミナルも、現在のposse-quiz-app/lib/quiz/terminalToken.ts:62は「指定されたコマンド列との一致」で進み、ファイルやGitの状態を更新するモデルではありません。将来はサーバーで初期状態から操作を再現し、最終状態
  と、学習目標上必要な操作を検査する方式が適切です。

  成績の扱いも変更が必要です。操作式は完成するまで提出できないため、現状では途中で何度失敗しても提出時は正解になります。選択式の初回正答率と混ぜず、初回正解・試行回数・ヒント使用・最終完了を分けて記録してくださ
  い。

  5．Supabaseを使う構成

  Supabase Auth・PostgreSQLは、認証と学習データの保存に適しています。推奨する役割分担は次のとおりです。

  React Native / Web
    ├─ Supabase Auth：ログイン
    ├─ 公開教材取得・本人の下書き保存
    └─ 採点API：回答確定
         ├─ 選択式・操作シミュレーションの採点
         └─ ジョブ登録 → 隔離したコード実行環境
                             ↓
                      採点結果・進捗をDBへ保存

  学習者のコードを、DBの管理権限を持つAPIプロセスで直接実行しないことが重要です。実行環境には認証トークンやSupabaseの秘密鍵を渡さず、通信・CPU・メモリ・出力量を制限します。端末のプレビューも、アプリ本体の認証情
  報やストレージから隔離します。

  Supabase Edge
  FunctionsにはCPU時間・メモリなどの制約があります。そのため、採点受付や軽い判定に使い、ブラウザを使うHTML/CSS/React採点は別の実行基盤へ渡す構成を勧めます。これは公式の制約を踏まえた設計判断です。公式ドキュメン
  ト (https://supabase.com/docs/guides/functions/limits)

  なお、Edge FunctionsはDeno互換ランタイムです。資料の「バックエンドはNode.js」を維持するなら、Node.js APIの配置先を別途決める必要があります。公式ドキュメント (https://supabase.com/docs/guides/functions)

  6．PostgreSQLのデータ設計

  「共通項目はカラム、形式固有の設定はjsonb」という方針に賛成です。最小でも、次の責務は分離したいです。

   データ                    保存する内容
  ━━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   教材・ドリル・ステップ    所属、順序、学習目標、公開状態
  ────────────────────────  ──────────────────────────────────────────────────────
   教材リビジョン            公開済みの問題・初期コード・素材・依存バージョン
  ────────────────────────  ──────────────────────────────────────────────────────
   非公開の採点定義          正解、テスト、採点器のバージョン
  ────────────────────────  ──────────────────────────────────────────────────────
   学習セッション            利用者、対象の版、現在ステップ
  ────────────────────────  ──────────────────────────────────────────────────────
   作業状態                  編集中のファイル、開始時点の状態、保存世代
  ────────────────────────  ──────────────────────────────────────────────────────
   提出                      提出時点の回答・コード・操作履歴。提出後は変更しない
  ────────────────────────  ──────────────────────────────────────────────────────
   採点結果                  状態、条件別結果、エラー、採点日時
  ────────────────────────  ──────────────────────────────────────────────────────
   進捗・復習                提出と採点結果から集計した学習状態

  user_id、外部キー、順序、状態、日時など、検索・認可・整合性に関わる項目は通常のカラムにします。ファイル定義や形式固有設定はjsonb、画像・大きな成果物はStorageが適切です。

  Supabaseでは、本人のデータをauth.uid() =
  user_idで制限するRLSを設定できます。ただし、本人の行だからといって採点結果まで本人が更新できる設計にはしないでください。正解は配信用テーブルから分離し、採点結果・進捗の確定はサーバーだけに許可します。RLS公式
  ドキュメント (https://supabase.com/docs/guides/database/postgres/row-level-security)

  通信再試行で成績が二重加算されないよう、提出には冪等キーを持たせます。採点結果の確定と進捗更新は同じDBトランザクションで処理する設計が必要です。

  7．保存・版管理で見落としやすい点

  現状、セッションと未確定入力はReact Contextのメモリ (posse-quiz-app/contexts/QuizSessionContext.tsx:85)にあり、永続化している進捗は主に集計値です。アプリ終了後の作業再開や過去コードの閲覧には足りません。

  さらに、問題本体はセッション開始時に複製していますが、操作式のActivityはカタログから別途解決 (posse-quiz-app/lib/quiz/terminalToken.ts:37)しています。問題だけを固定しても、参照先の版まで保証する構造にはなって
  いません。

  次をセットで固定してください。

  問題の版＋初期ファイル＋素材＋実行環境＋採点定義

  また、保存する下書きには世代番号を持たせ、複数端末からの更新で古いコードが上書きされるのを防ぎます。ログアウト・ユーザー切替時のローカルキャッシュ分離も必要です。

  オフラインについては、編集・練習は可能、正式採点はオンライン復帰後と定義するのが、新方針と整合します。
