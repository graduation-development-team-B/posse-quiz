# POSSE Quiz learning loop aligned to the reference learning architecture

The current POSSE Quiz implementation has a functional catalog-to-quiz-to-feedback-to-result loop, reusable accessible controls, responsive sizing, and semantic color tokens. Visually, it still reads as a utility dashboard: home has too many equal-weight actions, content detail lacks a strong catalog hero, and the quiz loop has no distinct immediate-review state. The two-tab shell and default stack headers also diverge from the reference navigation and immersive route transitions. Keep POSSE Week/Topic data and Japanese product copy, while replacing protected reference artwork and character copy with owned abstract treatments.

Watch for: **confirmed** navigation and header architecture diverge from the reference; **confirmed** home, detail, feedback, and result are structurally missing their primary visual hierarchy; **confirmed** scope labels ordinary Week selection as “おまかせ” without the adaptive behavior described by the reference.

**Verdict**: NEEDS_CHANGES

## High-level view

**Confirmed:** The global shell has only `ホーム` and `辞書`, rendered by the default Tabs bar, while the reference uses catalog/coach/data/account destinations and hides navigation during learning. Native headers also remain enabled for scope, feedback, and result despite custom surfaces on those routes.

**Confirmed:** Home presents discovery, launch, continuation, review, sync status, Week cards, Topic cards, weak topics, and another start button in one scroll. The catalog or continuation decision should come first, followed by one dominant start action; progress and secondary actions should be subordinate.

**Confirmed:** Content detail has progress, counts, tabs, and Topic states, but its hero is text-only and its Topic rows are generic cards. POSSE needs an owned visual Week anchor and a clearer numbered learning path.

**Confirmed:** The scope shell is already close to a mobile bottom sheet with a fixed footer CTA, but its selection model and “おまかせ” promise do not match the reference behavior. The quiz/result flow is serviceable; the major missing layer is a blue, session-level immediate-review experience before the final result.

### Global shell, bottom navigation, and route chrome

**Confirmed:** `app/(tabs)/_layout.tsx` exposes only `ホーム` and `辞書` through the stock Tabs bar. It has no floating/pill treatment, no catalog/coach/data/account destinations, and no explicit rule to hide navigation during learning. Move `設定` out of the home header into the account destination; move streak and longer-term progress toward data/coach rather than keeping them in the catalog’s first viewport.

**Confirmed:** `app/_layout.tsx` enables the default Stack header for `scope/index`, `feedback/[sessionId]`, and `result/[sessionId]`, while content and quiz explicitly hide it. `ScopeSheet` already draws a custom handle and sheet boundary, so use one chrome system: no native header above a custom surface, a consistent close/exit control, and no bottom tabs on scope, quiz, immediate review, or result. Keep tabs on catalog/detail/dictionary/account.

Validate the route sequence as `catalog → detail → scope sheet → quiz → immediate review → result`, with a back/close action returning to the previous catalog context. Keep the existing centered wide-screen and bottom-aligned compact `ScopeSheet` geometry.

### Catalog home: one decision before the long catalog

**Confirmed:** `app/(tabs)/index.tsx` puts title, settings, streak, two discovery buttons, launchpad, continuation, review, sync status, Week list, Topic list, weak topics, and a final `範囲を選んでクイズを始める` button into one vertical sequence. The same learning action appears as `おすすめの学習`, `今日の一歩を始める`, `続きから範囲を確認`, Week actions, Topic actions, and the final CTA.

Reorder the compact viewport as:

```text
catalog header/search affordance
  → continuation or one recommended learning card
  → catalog discovery / popular-new equivalent
  → Week catalog
  → weak topics and persistent review
```

Use one primary CTA in the recommended/continuation card. Keep Week cards as the catalog objects and make Topic cards secondary or detail-screen content. `WeekSummaryCard` has useful progress and availability states, but its `学習する` label, stats row, progress bar, and separate detail link should read as one card with one main tap target and one low-emphasis detail affordance.

**Likely:** search and popular/new entry points are stronger than the current generic outlined buttons. If search or ranking data is out of scope, use POSSE-specific affordances that route to existing catalog/scope behavior; do not imply unsupported search results or popularity data.

### Content detail: make the Week a catalog object

**Confirmed:** `app/content/[weekKey].tsx` renders a white text hero with percentage, title, generic description, Topic/question/term counts, and one CTA. It has no visual anchor equivalent to a cover, no category row, and no strong separation between hero and Topic progression. `LearningCard` rows show numbers and states but do not form an explicit path.

Add an owned visual anchor such as a colored Week-number tile, abstract geometric pattern, or POSSE curriculum mark. Overlay the existing progress percentage, then place title and compact metadata beside or below it. Use a two-line CTA that names the Week/Topic target while remaining POSSE-specific. Keep Topic order, muted unavailable rows, lock state, and trailing question volume; use tabs only where each tab has real POSSE data.

### Learning settings: keep the sheet, correct the promise

**Confirmed:** `ScopeSheet` already provides a mobile bottom sheet, centered wide-screen sheet, handle, scrollable body, and fixed footer. `scope/index.tsx` provides Week/Topic chips, selection summary, 3/5/10 question counts, and an always available start footer. Refine this structure instead of replacing it.

**Confirmed:** the help card says `おまかせで始められます` and promises efficient selection, but `startSession` still uses selected Week/Topic scope and the ordinary question pool. Rename it to `Week全体から出題` or implement a real mastery/date-aware scheduler. Do not copy the reference algorithm claim into a random pool.

Range chips should express only POSSE-backed data: Week-wide, selected Topic, unlearned, and review can appear when counts derive from progress/review state. Omit unsupported saved/weak modes rather than rendering imitations. Keep zero-question chips disabled, retain the fixed CTA, and show selected count in both chips and footer.

### Quiz: reduce the screen to one task

**Confirmed:** `ProgressHeader` already limits the top area to interruption and progress. `QuestionCard` adds format and `正解 n問` beside the prompt, while the page adds a separate submit CTA. This creates a form-like surface instead of the reference’s one-question focus.

Keep the prompt and answer controls central. Reduce correct-count feedback to quiet support or move it out of the primary reading path. Keep format labels only where they clarify `バグ診断` or `穴埋め`. Make submit sticky or consistently bottom-anchored on compact screens; retain full-width numbered radio hit areas.

**Possible:** the reference includes `SKIP`, but the current session model does not expose skip behavior. Do not add a visual-only button; define whether skipping records nothing, advances without feedback, and affects timing before implementing it.

### Feedback and immediate review: separate explanation from recovery

**Confirmed:** `feedback/[sessionId].tsx` changes background by correctness, then shows heading, progress, full question/options, full explanation, source, optional “なぜ違う？” and two actions. This is a per-question explanation surface, not the reference’s compact blue wrong-answer recovery step.

Keep explanation and source for per-question detail, but add a session-level immediate-review state for wrong answers accumulated in the current session. For an incorrect answer, show a blue review-context header, a compact list/grid of wrong Topic/question labels, and primary `間違えた問題を復習（N件）` plus a secondary result/continue action. Keep `/review` as the durable Review Queue; immediate review must use current-session wrong items without silently conflating the queues.

For correct answers, retain the warm progression state and continue to the next question or result. Preserve `正解`/`誤り`, explanation, and accessibility announcements; color should reinforce, not carry, state.

### Result: celebrate completion, then expose the next action

**Confirmed:** `result/[sessionId].tsx` uses a pale achievement background and `ResultSummary` makes `正解数 correct / total` primary; retry, review, home is the right broad action order. The result is visually restrained and `ResultMetrics` lists incorrect Topics rather than concrete wrong items.

Give the score a larger numeric treatment with a smaller unit/label, then place elapsed time and review count in secondary cards. Add a wrong-question or wrong-Topic section with enough context to start immediate/persistent review. Do not reproduce reference characters, paper-confetti, or exact praise copy. Keep empty Review disabled with an explanatory label.

**Confirmed:** the result model has elapsed time, review count, incorrect Topics, and score, but no date-indexed daily total. Do not add `本日の累計` from all-time week totals; add date-aware storage separately or omit the metric.

### Shared visual system: cards, spacing, type, and semantic color

**Confirmed:** `constants/theme.ts` defines the right broad meanings—orange progression, blue review, green growth, gray support, white surfaces—but screens still hard-code `#F3F4F6`, `#C2410C`, `#075985`, `#9A3412`, and `#B91C1C`. Card radii range from 14 to 28, borders appear on most surfaces, and the shared 16/20/32 type scale under-emphasizes numeric progress/result values.

Create shared tokens for page background, white/elevated surface, card/control radii, 8/12/16/24 spacing, border/elevation, supporting text, and numeric display type. Prefer whitespace and surface contrast over a border on every card. Apply orange to forward/selected/progress, blue to review/recovery, green to growth increments, and gray to unavailable/supporting states across all five screens.

Preserve `ResponsiveScrollView` and the 960px cap. Test the reference mobile viewport with fixed footer/tab bar and safe-area insets so the home stack and footer do not compete for space.

### Protected reference material boundary

**Structural/visual work safe to implement:** catalog-first ordering, four-destination navigation, modal-like scope, custom route chrome, owned Week blocks, numbered progression, fixed primary CTAs, compact metric cards, semantic colors, larger numeric hierarchy, and immediate-review grouping.

**Do not copy:** book covers, character illustrations, blur/character treatments, logos, proprietary icons, exact praise slogans, user-name copy, premium/marketing language, or reference artwork. Use POSSE Week/Topic titles, POSSE-specific Japanese microcopy, and abstract/original visual blocks. Treat any needed illustration as a new owned-asset request.

### Implementation order and acceptance checks

**P0:** fix route chrome/tab visibility; collapse home to one dominant action; correct the scope promise; introduce immediate review. **P1:** rebuild detail hero/progression and result hierarchy; apply shared visual tokens. **P2:** add only supported discovery affordances, date-aware metrics if designed, and owned artwork.

Visual comparison is ready when catalog/detail retain navigation while scope/quiz/review/result do not; scope opens as one sheet without duplicate header; home’s first viewport has one obvious start/continue action; detail has an owned Week anchor and numbered Topic path; quiz shows one question with quiet progress; wrong answers enter a blue immediate-review state; result makes score and next action dominant; and no reference artwork or copy is imported.
