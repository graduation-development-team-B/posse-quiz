# Week11｜AIリテラシー：AIの答えを自分のものにする

プログラミングで詰まったとき、エラー文をAIに貼ってみる。返ってきたコードをコピーして貼り付けたら、直った。Week06でJavaScriptに入ってから、こういう場面が増えてきました。

直ったのはいいことです。でも「なぜ直ったの？」と聞かれて、すぐ答えられるでしょうか。答えられないなら、そのコードはまだ自分のものになっていません。動いてはいるけれど、中身は借り物のままです。そのままにしておくと、次に似た場面が来ても、やっぱり自分では書けません。エラーを一つ乗り越えるたびに書ける範囲は広がっていくのに、答えだけもらっていると、その広がりが手元に残らない。何回AIに直してもらっても、自分でできることは増えないままです。

今週やるのは、これを自分のものに変える手順——AIに答えだけ出させるのではなく、AIと一緒に考えるやり方です。AIはこれからも、Week16では本格的に使います。だからこそ、受け取った答えを自分のものにするやり方を、ここで身につけておきます。

## インプット

### 直った。でも、なぜ直ったかは言えますか

エラーをAIに貼って、返ってきたコードで直った。よくある場面です。ではここで、ひとつ試してみてください。

いま自分のリポジトリを開いて、これまでにAIへ手伝ってもらったコードを、どこでもいいので1つ見つけます。見つけたら、AIを閉じて、そのコードを上から1行ずつ、声に出して説明してみる。「この行は○○をしていて、ここは△△で……」と。

途中で詰まった行は、ありませんでしたか。「なんとなく動いてるけど、この行が何なのかは説明できない」。そこが、まだ自分のものになっていない部分です。

借り物か、自分のものか。見分け方は2つです。

- その内容を、**AIを閉じた状態で、自分の言葉で説明できるか**
- そのコードを、**少し変えても自分で直せるか**

どちらも怪しいなら、まだ借り物の段階です。AIの説明はうまいので、読むと「なるほど、そういうことか」とスッと腑に落ちます。でも、腑に落ちたことと、自分で書けることは別です。分かった「気」だけが残って、次に似た場面が来たとき、また同じところで詰まる。これが、分かった気でいることのこわさです。

だから線を引いておきます。**説明できないコードを、自分の作品に残さない。** これは見栄えの問題ではなく、あとで自分が困らないための線引きです。今週は、これを自分のものに変えるやり方を、最後まで通してやっていきます。

---

### 「いい感じにして」では、いい感じにならない

AIが的外れな答えを返すのは、賢くないからではありません。**AIには、あなたの頭の中が見えないから**です。本当は何をしたいのか、どのコードのどこで困っているのか、どこまで触ってほしいのか——それはあなたの頭の中にあって、口に出して渡さないかぎり、AIには分かりません。分からない部分を、AIは"いちばんありそうな線"で勝手に埋めます。だから「このコードをいい感じにして」だけ投げると、目的を想像で補って、的外れな大改造を返してくる。

AIに渡し忘れがちなのは、いつもこの3つです。

- **目的**：本当は何をしたいのか
- **対象**：どのコードの、どこの話なのか
- **範囲**：どこまで直してよくて、どこは変えてほしくないか

この3つを先に渡すだけで、AIは驚くほど外さなくなります。欲しい答えを引き出すコツは、**何を・どの観点で・どこまで見てほしいか**を、こちらから渡すことです。

型にすると、こうなります。

```
目的:
前提:
見てほしい観点:
制約:
出力形式:
```

たとえば、フォームのバリデーションをレビューしてほしいとき。

```
目的: ユーザー登録フォームのJSバリデーションをレビューしてほしい
前提: HTML/CSS/JSだけで書いている。Reactなどは使っていない
見てほしい観点: バリデーションの漏れ、エラーメッセージの分かりやすさ
制約: 大きな作り直しではなく、今のコードの改善候補を出してほしい
出力形式: 指摘・理由・確認方法を、表で
```

前提（HTML/CSS/JSだけ）を渡したから、AIは見当違いのReactコードを返さずに済みます。制約（大改造はしない）を渡したから、課題の範囲を超えた作り直しを防げます。文脈を渡すというのは、AIが想像で埋めてしまう穴を、先回りでふさいでおくことです。

---

### これだけは、絶対に渡さない

渡す側には、2つの仕事があります。ひとつは、いまやった「必要な文脈は渡す」。もうひとつが、その反対——**絶対に渡してはいけないものを、渡さない**ことです。

SNSに上げた写真は、消したつもりでもどこかに残っているかもしれない。一度口にした言葉は、なかったことにできない。AIへの入力も、同じだと思っておくのが安全です。サービスによっては、入力した内容が保存され、学習に使われることもあります。渡してから後悔しても遅いので、渡す前に止めます。

絶対にAIに貼ってはいけないもの、という線をはっきり引いておきます。

**個人情報**：本名、住所・電話番号、メールアドレス、顔写真、そして他人の情報。
**機密情報**：パスワード、APIキー・アクセストークン、`.env` の中身、非公開URL、privateリポジトリの中身。

特に、Week10で触ったGitHub APIのトークンのような「本物の鍵」。これをそのままAIに貼るのは、家の鍵を写真に撮ってネットに上げるのと同じです。相談したいなら、具体的な値を消して、架空の値に置き換えてから渡します。

```
悪い例：
API_KEY=sk-xxxxxxxxxxxx

良い例：
API_KEY=ここにAPIキーが入ります
```

サービスの設定に**オプトイン**（自分が許可したときだけ学習に使われる）や**オプトアウト**（使われたくないので自分で切る）の項目があれば、確認しておくとなお安心です。ただし、設定をいじる前に、そもそも渡さない。これがいちばん確実な防御です。なお、AIが生成したコードや文章は、権利の扱いがサービスや使い方で異なります。採用するなら、中身を理解してからにしましょう。

---

### 完成品より、"なぜ"をもらう

ここからは、受け取り方の話です。

AIにコードを直してもらうとき、いちばん簡単なのは「全部書き直して」と頼んで、返ってきた完成コードをコピペすることです。動きます。早い。でも、それをやった瞬間、動くけれど説明できないコードが、そっくり手元に残ります。この章のはじめに見た、あの状態です。

だから、頼み方をひとつ変えます。**完成品を丸ごともらうのではなく、"なぜ"をもらう。**

たとえば、自分の書いたコードをAIに直してもらったとします。返ってきたコードをそのまま貼る前に、こう聞いてみる。

```
なぜこの書き方にしたんですか？
この行は何をしていますか？
他のやり方はありますか？それと比べて、なぜこれですか？
```

返ってくるのは、コードではなく説明です。「ここは○○だからこう書いた」「この行は△△している」。それを読むと、さっきまでブラックボックスだったコードの中身が、少しずつ見えてきます。

"なぜ"を聞いて、自分の言葉で言い直せるようになった時点で、そのコードはもう借り物ではありません。**自分のものに変わっています。** これが、この章のはじめに出した2つのテスト——「AIを閉じて説明できるか」「少し変えても直せるか」——に、自分から近づいていく方法です。完成コードを丸ごともらうと、テストに落ちる側へ進む。"なぜ"をもらうと、テストに受かる側へ進む。同じAIを使っていても、頼み方ひとつで、借り物が増えるか、自分のものが増えるかが分かれます。

---

### 全部は、受け取らない

"なぜ"を聞いて中身が見えたら、最後に仕分けます。AIから返ってきた答えを、そのまま全部取り込む。これがいちばんやってはいけないことです。受け取る前に、まず4つに分けます。

| 仕分け | どういうとき |
|---|---|
| 採用する | 目的に合っていて、自分でも確認できた |
| 保留する | 良さそうだが、今の課題の範囲を超えている |
| 採用しない | 目的に合わない、または間違っている |
| 要確認 | 正しいか判断できないので、自分で調べる |

このうち、**「採用しない」と言えることが、いちばん大事です。** AIを使いこなす力とは、全部を受け入れる力ではなく、いらないものを断れる力のことだからです。

仕分けたら、記録に残します。何を渡し、何を聞き、どう判断したか。この記録は、AIを使ったことを反省するためのものではありません。あとで読み返したとき、そこに残っているのはAIの賢さではなく、あなたの判断の跡です。記録のひな形は、後ろのPOSSE課題に用意してあります。

---

### AIに、答えを出させない使い方

最後に、AIの使い方を一段上げます。ここまでは「返ってきた答えをどう扱うか」でした。最後は、そもそもの頼み方の話です。

説明できないコードがいちばん増えるのは、AIに答えそのものを出させたときです。だったら、逆をやればいい。**答えを出させず、自分に考えさせる**ように頼みます。

具体的には、プロンプトでこう指示します。

```
答えのコードは出さないでください。
進め方のヒントと、考える順番だけ教えてください。
コードは自分で書きます。詰まったら、また聞きます。
```

こう頼むと、AIは完成コードの代わりに、足場を作ってくれます。「まず○○を考えてみて」「次は△△が要るはず」。手を動かして書くのは自分。AIは、答えを教える先生ではなく、横で考える順番をヒントにくれる相手になります。これだと、出来上がったコードは最初から自分のものです。借り物が、そもそも生まれません。

実は、これを最初からやってくれる機能もあります。ChatGPTには「学習モード（Study mode）」、Claudeにも「学習モード」があり、オンにすると答えを即出さず、質問を返しながら考えさせてくれます。GitHub Copilotのように専用のボタンが無いツールでも、いま書いたように「答えは出さず、ヒントだけ」と指示すれば、同じ状態を自分で作れます。機能の名前やある・なしはツールごとに変わりますが、やっていることは同じ。**「AIに答えを出させず、自分に考えさせる」。これはどのAIでも、プロンプト一つで作れます。**

ここで、AIに任せていい所と、自分でやる所を整理しておきます。

**AIに任せていい（得意で、任せても自分の力は落ちない）：**
- コードの読み方やエラー文の意味を説明してもらう
- 改善案を複数出してもらう
- 自分が気づかなかった確認観点を出してもらう
- 似た書き方の違いを比べてもらう

**自分でやる（ここを手放すと、力がつかない）：**
- 実際に手を動かしてコードを書く
- どれを採用するか判断する
- 動かして、自分の目で確かめる

AIを使うほど自分の力が落ちる人と、AIを使うほど力が伸びる人がいます。違いは、この線引きを持っているかどうかです。

---

### 今日のまとめ

- AIが外すのは、賢くないからではなく、あなたの頭の中（目的・対象・範囲）が見えないから。渡さなければ、AIは"ありそうな線"で勝手に埋める。流暢でも自信ありげでも、正しさの証拠にはならない（存在しない機能をでっち上げる「ハルシネーション」もある）。
- 借り物を自分のものに変えるのは、"なぜ"を聞くこと。完成コードを丸ごともらわず、なぜこの書き方かを聞き出して、自分の言葉で言い直せたら、それは自分のもの。
- 渡す前に止めるもの（個人情報・トークン）と、受け取る前に仕分けるもの（採用・保留・採用しない・要確認）を、習慣にする。

そして今日から、AIに手伝ってもらったら毎回これをやります。「途中を聞いて、自分のものにする」。来週からのライブラリやReactでも、AIに使い方を聞く場面は必ず出てきます。そのたびに、答えだけ受け取るか、"なぜ"まで聞くか。その選び方しだいで、AIはあなたの力を奪う道具にも、伸ばす道具にもなります。

## 今週の深掘り問題（ミニドリルの代替・AI禁止・30分）

今週はコーディング課題の代わりに、自分のコードと向き合う問題です。AIには頼らず、自分の手と頭だけで答えてください。

### 問題1：借り物を、自分で見つける（15分）

Week06〜Week10の自分のコードから、AIに手伝ってもらった部分を1つ選び、AIを閉じた状態で、次の2つのテストをやってみてください。

```
1. その部分を、上から1行ずつ自分の言葉で説明する。
   - 詰まらず最後まで説明できたか？
   - 説明できなかった行があれば、それはどこか。
2. その部分を少しだけ変えてみる（例：表示する項目を1つ増やす、条件を1つ加える）。
   - AIに頼らず、自分で直せたか？
   - 直せなかったなら、何が分からなくて手が止まったか。
```

詰まった行・手が止まった場所が、いまのあなたに残っている「借り物」です。それがどこだったかを、正直に書き出してください。

### 問題2：プロンプト改善の下書き（15分）

これまで自分がAIに出した指示文（プロンプト）のうち、「曖昧だったな」と思うものを1つ選びます。何が曖昧だったかを説明したうえで、今週学んだ「良いプロンプトの型」で書き直してください。

```
元のプロンプト:

何が曖昧だったか:

改善版：
  目的:
  前提:
  見てほしい観点:
  制約:
  出力形式:
```

この改善版は、後でPOSSE課題で実際にAIへ送って試します。

## POSSE課題

### テーマ：AIと考えた1セッションのログ（Markdownファイルの提出）

**今週はHTMLファイルではなく、Markdownファイル（`.md`）をPR提出します。**

GitHubリポジトリに `week11-ai-log.md` というファイルを作り、以下の内容を書いてPRを出してください。今週のやり方を、実際に1回まわしてみるのがねらいです。

**要件:**

**Part 1：AIと考えた1セッション（実践）**

小さなテーマを1つ決めて、AIと1セッション対話します。テーマは何でも構いません（例：Week10で書いた自分のコードの一部をレビューしてもらう／ある書き方の意味を聞く／小さな機能の進め方を相談する）。そのセッションを、今週のやり方で進めて記録します。

- 「良いプロンプトの型」で指示を出す（深掘り問題で書いた改善版を使ってもよい）
- 返ってきた出力に対して、**"なぜ"を最低1回は聞く**（「なぜこの書き方か」「この行は何か」など）
- "なぜ"を聞いて、**自分が新しく分かったこと**を書く（聞く前は分からなかったが、聞いて説明できるようになったこと）
- 出力を4分類（採用・保留・採用しない・要確認）に分け、判断理由を書く。**「採用しない」または「要確認」を最低1つ**入れること

**Part 2：流された場面の振り返り（短く）**

これまでの学習で、AIの出力を「よく分からないまま採用してしまった」場面を1つ思い出して、1〜3文で書きます。どのWeekの何で、なぜ流されたのかが分かれば十分です（思い当たらなければ、その旨と理由を書く）。

**Part 3：今後のAI利用方針**

- Week11を通じて気づいたことを1〜3文でまとめる
- 今後のPOSSE課題でのAI利用の自分ルールを書く（「インプットでは使わない」「完成コードは丸ごともらわず"なぜ"を聞く」など）

**提出:**
- GitHubリポジトリURL（`week11-ai-log.md` が含まれるPRのURL）

**PR本文に必ず書くこと:**
1. Part 1で、"なぜ"を聞いて新しく分かったことの概要（1〜3文）
2. 「採用しない」または「要確認」に分けた出力と、その理由
3. 今後自分が意識したいAI利用のルールを1つ

### AI出力を判断する観点

| 観点 | 確認すること |
|---|---|
| 動くか | 実際にコピーして動かし、エラーが出ないか確かめたか |
| 説明できるか | "なぜ"を聞いて、そのコードを自分の言葉で説明できるか・少し変えても直せるか |
| 範囲が合っているか | 課題の範囲を超えた大きな作り直しになっていないか |
| 安全か | 個人情報・機密情報を渡していないか |
