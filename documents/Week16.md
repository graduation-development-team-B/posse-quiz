# Week16｜AIコーディング実践

PH1もいよいよ最終週です。ここまでで、HTMLでページを組み、Tailwindで見た目を整え、JavaScriptで動きをつけ、Reactで画面を部品に分けて状態を持たせる——ひととおり、自分の手で作れるようになりました。Week11では、AIの答えを「借り物」のままにせず、"なぜ"を聞いて自分のものに変えるやり方も学びました。

今週は、その総仕上げです。テーマを自分で決めて、AIと組んで、作品をひとつ作りきります。ひとつだけ、はっきりさせておきたいことがあります。今週は「AIに作らせる週」ではありません。**AIと一緒に作って、最後に、できたものを自分の言葉で説明できる状態にする**。これが今週のゴールです。作るだけなら、AIに丸投げしても動くものは出てきます。でも、それはあなたの作品ではなく、AIの出力を受け取っただけです。その差を埋めるのが、今週やることです。

## インプット

### まず丸投げしてみる

いきなりですが、ひとつ試してみてください。

自分のAIツールを開いて、こう打ちます。「Reactでタスク管理アプリを作って」。それだけ。数秒待つと、それらしいコードが、すらすらと返ってきます。`useState` があって、追加ボタンがあって、一覧が並んでいて、たしかにタスク管理アプリのコードに見えます。

では、そのままAIを閉じてください。そして、返ってきたコードを上から3〜4行、自分の言葉で説明してみます。「この行は○○をしていて、ここは△△で……」。

最後まですらすら説明できたでしょうか。たぶん、どこかで言葉に詰まります。「動きそうだけど、この行が何なのかは、はっきり言えない」。Week11で見た、あの感覚です。あのときはAIに手伝ってもらった数行が借り物でした。今回は、アプリまるごとが借り物になっています。規模が大きくなっただけで、起きていることは同じです。

だから今週は、この「借り物のまま」を作らないための習慣を、4つに分けて身につけます。要件を自分で書く。返ってきたら読む。動かないときは症状を見せる。最後に、自分の言葉で説明できるようにする。順番に見ていきます。

---

### 「作って」だけでは、作りたいものは出てこない

さっき「タスク管理アプリを作って」で返ってくるものは、たいてい、頭に描いていたイメージと少しずれています。色も、機能も、ファイルの分け方も、こちらが何も言わないうちに決められている。

AIが的外れなものを返すのは、賢くないからではありません。**AIには、あなたの頭の中が見えないから**です。何を作りたいのか、どんな機能が要るのか、どこまで作ってほしいのか——それはあなたの頭の中にあって、口に出して渡さないかぎり、AIには分かりません。分からない部分を、AIは"いちばんありそうな線"で勝手に埋めます。だから「作って」だけ投げると、想像で補った平均的な何かが返ってくる。

やることは、逆です。**渡す前に、作りたいものを自分の言葉で分解して、先に書き出す。**

```
悪いプロンプト：
タスク管理アプリを作って
```

```
良いプロンプト：
Reactで作るタスク管理アプリです。次の機能が欲しいです。
- 入力フォームと追加ボタンで、タスクを追加できる
- タスクをクリックすると、完了状態に切り替わる
- 完了したタスクは、打ち消し線で表示する
- 削除ボタンで、タスクを1件消せる
- 状態は useState で管理する
- 見た目は Tailwind で整える

App.jsx のコードを書いてください。
```

分解して渡すほど、返ってくるものが、頭の中のイメージに近づきます。この「作りたいものを明確にする」スキルは、AIがいなかった時代からずっと大事だったものです。AIが来て、むしろ効き目がはっきりしました。

型にすると、こうなります。実装を頼むときは、この順で書くと過不足が減ります。

```
実装依頼の型：
[技術スタック]で[作るもの]を作っています。
いまは[現在の状態]です。
[追加・修正したいこと]をお願いします。
[守ってほしい制約・条件]があります。
```

この「作る前に要件を書き出す」工程は、今週のPOSSE課題で必ずやってもらいます。コードを書き始める前に、分解表を1枚うめてから、AIに指示する。それが今週の作り方です。

---

### 返ってきたコードは、貼る前に読む

要件を渡して、コードが返ってきた。ここでいちばんやりがちなのが、中身を見ずにそのまま貼り付けることです。動けばラッキー。でも、動かなかったとき、あるいは後から少し直したくなったとき、自分が何を貼ったのか分からないと、手も足も出ません。Week13からReactまで、さんざんエラーと格闘してきました。あの、どこを直せばいいか分からない詰まりの手触りは、もう知っているとおりです。

だから、採用する前に、最低でもこの3つは目で追います。

- どんな関数・コンポーネントが作られているか
- 状態（state）は何で、それが何をきっかけに更新されるか
- 自分のプロジェクトのファイル構成と合っているか（`import` のパスは正しいか、使っているライブラリはインストール済みか）

読んでから採用する習慣が、そのまま「AIが壊したコードを、自分で直せる力」になります。逆に、読まずに貼る回数が増えるほど、説明できないコードが静かに積み上がっていきます。

---

### 「動かないです」では、AIも困る

読んで、貼って、動かした。エラーが出た。ここでAIに戻って「動かないです」とだけ伝えても、AIはどのエラーのことか分かりません。あなたの画面が見えていないのは、さっきと同じです。

エラーが出たときは、**症状をそろえて見せます**。

```
デバッグ依頼の型：
次のエラーが出ています。

[エラーメッセージをそのままコピペ]

該当するコードはこちらです。

[エラーが起きているコードを貼る]

自分では[試したこと]をやってみましたが、直りませんでした。
原因と、修正方法を教えてください。
```

エラー文とコードと「試したこと」をセットで渡すと、AIの回答は一気に的確になります。Week10で、`response.json is not a function` のようなエラー文をちゃんと読むと原因にたどり着けた——あのときと同じで、エラー文は捨てずに、まるごと渡すのが正解です。

もうひとつ、面白いことが起きます。症状を言葉にしてまとめているうちに、AIが答えるより先に、自分で原因に気づくことがあります。「あ、ここ `await` 付け忘れてる」と。これは**ラバーダック・デバッグ**と呼ばれるやり方で、机の上のゴムのアヒルに向かって、困っていることを声に出して説明すると、頭が勝手に整理されて答えが見えてくる、という古くからの手です。AIは、そのアヒルの上位互換になります。黙って聞くだけでなく、こちらが整理し終えたら、ちゃんと答えも返してくれるからです。

---

### 最後に問われるのは、「これ、何してるの？」

作品ができて、PRを出す。すると、レビューでこう聞かれます。「この部分、何をしているんですか？」

授業で当てられた場面を思い出してください。自分で考えて書いた答えは、すっと言葉が出てくる。でも、よく分からないまま人の答えを写しただけのところは、そこだけ口ごもる。急に背中が冷たくなる、あの感じ。コードでも、まったく同じことが起きます。AIが書いた行を、中身を分からないまま残していると、「これ何してるの？」の一言で固まります。

だから、Week11でやったことを、ここでもう一度やります。**AIを閉じて、そのコードを自分の言葉で説明してみる。少しだけ変えて、自分で直せるか試してみる。** このどちらも通れば、そのコードはもう借り物ではありません。自分のものになっています。

説明できない行が見つかったら、道は2つです。消すか、分かるまで聞くか。聞くときは、こう頼みます。

```
説明依頼の型：
このコードの[この部分]が何をしているのか、初学者にも分かるように説明してください。
自分は[こう理解している]のですが、合っていますか？
```

自分の理解を添えて聞くのがコツです。まるっと「説明して」より、ズレているところをAIがピンポイントで直してくれます。完成コードを丸ごともらうのではなく、"なぜ"をもらう。Week11で通したこのやり方が、そのまま今週の完了条件になります。

そして、PR本文には「どんなプロンプトを送ったか」「AIの提案を採用しなかった箇所と、その理由」を書いてもらいます。これは反省文ではありません。あとで読み返したとき、そこに残っているのはAIの賢さではなく、**あなたが何を採り、何を断ったかという判断の痕跡**です。

---

### 貼る前の、最後の見直し

AIが生成したコードを採用する前に、ざっと通す見直しリストです。ミニドリルで実際にやることの、予告編でもあります。

| チェック項目 | 確認方法 |
|---|---|
| 動くか | `pnpm run dev` で起動して、ブラウザで実際に動かす |
| `import` のパスが合っているか | 自分のプロジェクトのファイル構成と照らし合わせる |
| 使っているライブラリを入れてあるか | `package.json` を見て、`import` しているものがそこにあるか確認する |
| 状態を直接書き換えていないか | 配列や状態を `push` などで直接いじっていないか（Week15の鉄則） |
| 一覧に `key` が付いているか | `map` で並べた要素に、固有の `key` があるか |
| 古いバージョンの手順が混ざっていないか | Tailwindなら `tailwind.config.js` を作れと言ってこないか（それはv3の手順。Week13で入れたのはv4） |
| スタイルの当て方が今のやり方と揃っているか | Tailwindのクラスで組んでいるか（AIは素のCSSファイルを別に作る書き方をよく出してくる） |
| 説明できない部分はないか | 1行ずつ「これは何をしているか」を、自分の言葉で言えるか |

いちばん下の「説明できない部分はないか」が、結局いちばん大事です。ほかの項目は、これができていれば自然に見つかります。

### 今日のまとめ

- AIが外すのは、賢くないからではなく、あなたの頭の中が見えないから。だから、作りたいものを自分の言葉で分解して、先に渡す。丸投げは、借り物を1つ増やすだけ。
- 返ってきたコードは、貼る前に読む。動かないときは、エラー文とコードと試したことをそろえて見せる。「動かないです」だけでは、AIも困る。
- 最後に問われるのは「これ何してるの？」。AIを閉じて自分の言葉で説明できて、少し変えても直せる。そこまで来て、はじめてあなたの作品になる。説明できないコードは、作品に残さない。

今日から、AIに手伝ってもらったら毎回これをやります。「途中を聞いて、自分のものにする」。PH1はここで終わりますが、この習慣は、道具が変わっても、これからずっと効きます。

## ミニドリル（AI禁止・30分）

### AIが生成したコードのレビュー問題

今週は、AIが生成したコードを**自分の目で**レビューします。AIには頼らず、自分の手と頭だけで答えてください。ここは、AIを使わずに「AIのおかしな出力を見抜けるか」を確認する場です。

以下は、「Reactでタスク管理アプリを作って」と頼んだときに返ってきそうな、一見ちゃんと動きそうなコードです。実際、これらは AI が生成するコードによく混じる書き方ばかりです。問題点・改善すべき箇所を見つけて、理由とともに説明してください（複数あります。見つけられるだけ挙げてください）。

```jsx
import { useState } from "react";

function App() {
  const [tasks, setTasks] = useState([]);
  const [input, setInput] = useState("");

  const addTask = () => {
    tasks.push({ text: input, done: false });
    setTasks(tasks);
    setInput("");
  };

  const deleteTask = (index) => {
    tasks.splice(index, 1);
    setTasks(tasks);
  };

  return (
    <div style={{ padding: "20px" }}>
      <h1 style={{ color: "red" }}>タスク管理</h1>
      <input
        style={{ border: "1px solid black" }}
        onChange={(e) => setInput(e.target.value)}
      />
      <button style={{ color: "white", background: "blue" }} onClick={addTask}>
        追加
      </button>
      <ul>
        {tasks.map((task, index) => (
          <li>
            {task.text}
            <button onClick={() => deleteTask(index)}>削除</button>
          </li>
        ))}
      </ul>
    </div>
  );
}

export default App;
```

<details>
<summary>解答例（全部見つけられなくても大丈夫）</summary>

**問題1：配列を直接書き換えている（最重要）**

`tasks.push(...)` と `tasks.splice(...)` は、いまある配列そのものを直接いじっています。しかも `setTasks(tasks)` は、中身をいじった配列を、同じ入れ物のまま渡し直しているだけ。Reactは「入れ物（参照）が変わったか」で画面を描き直すかどうかを判断するので、この `setTasks` は「何も変わっていない」と見なされます。Week15でやった「状態は直接いじらず、新しいものを作って渡す」の鉄則を破っています。

やっかいなのは、**追加だけは動いているように見える**ことです。`addTask` は最後に `setInput("")` を呼んでいて、こちらは本当に値が変わるので描き直しが起きる。その巻き添えで、直接いじった `tasks` の中身も画面に出てしまいます。一方 `deleteTask` は `setTasks(tasks)` しか呼ばないので、描き直しが起きず、削除しても消えません。「追加は動くのに削除だけ効かない」という、原因の見えにくいバグになります。

修正：スプレッド構文と `filter` で、新しい配列を作って渡す。

```jsx
// 追加
setTasks([...tasks, { text: input, done: false }]);

// 削除
setTasks(tasks.filter((_, i) => i !== index));
```

**問題2：`map` に `key` が無い**

一覧の `<li>` に `key` が付いていません。Reactの警告（`Each child in a list should have a unique "key" prop.`）が出て、要素の増減で表示がおかしくなることがあります。

修正：固有の `id` を持たせて、それを `key` に使う。

```jsx
setTasks([...tasks, { id: Date.now(), text: input, done: false }]);
// <li key={task.id}> のように使う
```

**問題3：入力欄が制御されていない（controlled でない）**

`<input>` に `value` が設定されていません。`onChange` で `input` の状態は更新されますが、入力欄の表示とはつながっていないので、`setInput("")` でクリアしても、入力欄の文字が消えません。

修正：`value={input}` を追加して、状態と表示をつなぐ。

**問題4：スタイルを全部インラインで書いている**

`style={{ ... }}` を要素ごとに直接書いています。数が増えるほど読みにくく、直しにくくなります。TailwindのクラスやCSSファイルに寄せると、管理がぐっと楽になります（必須ではないが、改善点）。

**問題5：`index` を削除の目印にしている**

配列の `index` でタスクを消しています。並び順が変わると、`index` は別のタスクを指すようになり、意図しないタスクが消えることがあります。`index` ではなく、固有の `id` で消す方が安全です。

</details>

## POSSE課題

### テーマ：自由制作（AIと作って、自分で説明できる状態にする）

PH1で学んだ技術（HTML/Tailwind/JavaScript/React）を組み合わせて、自分でテーマを決めた作品を作ります。AIを積極的に使ってかまいません。ただし今週の主役は、動いた作品そのものよりも、**「どう作り、何を採り、何を断り、それをどこまで自分で説明できるか」を書いたPR本文**です。ここを読めば、あなたがAIと組んで、その成果を自分のものにできたかどうかが分かる——そういうPRを目指します。

**テーマの例（自由に選んでOK）:**

- ポートフォリオサイト（Week12のものをReactで作り直す）
- 日記・メモアプリ（`localStorage` で保存する）
- クイズアプリ（問題と答えをReactで管理する）
- 天気を表示するページ（`fetch` + `useEffect`。Week10・Week15の発展）
- カウントダウンタイマー
- ランダムおみくじアプリ
- そのほか、自分が作りたいと思ったもの

**要件:**

- テーマを自分で決める（前週までとは別の、新しいプロジェクトを作る）
- PH1で学んだ技術（HTML/Tailwind/JavaScript/React）を使う
- **コードを書き始める前に、下の「要件分解表」を1枚うめる**（AIに指示するのは、そのあと）
- AIを積極的に使ってよい
- 説明できないコードを残さない（分からない箇所は、AIに"なぜ"を聞くか、削除する）
- 動くものを公開する（Viteでビルドし、GitHub Pagesで公開。うまくいかなければリポジトリURLでも可。Week13でやった `vite.config.js` の `base: './'` 設定を忘れずに）
- DevToolsで、スマホ幅（375px）とPC幅（1280px）の両方で表示を確認する

**実装前にやること：要件を自分の言葉で分解する**

いきなりAIに「作って」と投げず、まず次の表をうめます。これが鉄則1の実践です。うめ終わった表は、そのままAIへの最初のプロンプトの材料になります。

| 項目 | 書くこと |
|---|---|
| 何を作るか | 一言で言うと、どんな作品か |
| 画面に出すもの | 何が表示されるか（一覧・入力欄・ボタン・画像など） |
| できる操作 | ユーザーは何をクリック・入力できるか |
| 持つ状態（state） | 画面のどの値が変わるか（タスク一覧・入力中の文字・現在の得点など） |
| 使う技術 | React／`useState`／`useEffect`／`fetch`／`localStorage` などのうち、どれを使うか |
| つまずきそうな所 | 書く前から不安な箇所（あれば） |

**【発展・任意】**

- `useEffect` と `localStorage` で、リロードしてもデータが残るようにする
- `fetch` で外部APIからデータを取ってきて表示する（天気・名言・画像など）
- 複数のコンポーネントに分けて、`props` でデータを渡す構成にする

**提出:**

- GitHubリポジトリURL
- GitHub PagesのURL（公開できなかった場合は、その旨と理由）

**PR本文に必ず書くこと（今週の主役はこれです）:**

1. 作ったものの概要と、工夫した点（何を作って、どこにこだわったか）
2. AIに送ったプロンプト（**3つ以上**。実際に送ったものを、そのまま貼る）
3. AIの提案を採用しなかった箇所と、その理由（**1箇所以上**。「AIはこう出したが、こういう理由で使わなかった／こう直した」）
4. 自分で理解していない箇所が無いことの確認（**1箇所以上**。「〜の部分は、こういう意味だと理解した」の形で、AIを閉じても説明できることを示す）
5. PH1全体を通じて、いちばん面白かった・難しかった技術や体験

## 参考資料

教材を読み終えてから、必要に応じて参照してください。

### プロンプトの型（3種）

| 場面 | 型 |
|---|---|
| 実装を頼む | 技術スタック・現在の状態・やりたいこと・制約 を渡す |
| デバッグを頼む | エラー文・該当コード・試したこと を渡して、原因と修正を聞く |
| 説明を頼む | 対象箇所・自分の理解 を添えて、合っているか聞く |

### AIと組んで作るときの見直し観点

| 観点 | 確認すること |
|---|---|
| 動くか | 実際に `pnpm run dev` で起動して、ブラウザで動かしたか |
| 説明できるか | AIを閉じて、そのコードを自分の言葉で説明できるか・少し変えても直せるか |
| 状態の扱い | 配列や状態を直接書き換えていないか（新しいものを作って渡しているか） |
| 安全か | 個人情報・APIキーなど、渡してはいけないものをAIに貼っていないか（Week11） |
